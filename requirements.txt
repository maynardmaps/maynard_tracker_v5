1) Be as lightweight to open as possible so as to work with limited connectivity.
2) Be compatible with being hosted on github as a webpage.
3) Display a map to the user. See "map requirements" section for details.
4) Be responsive and work well on both desktop and mobile devices.



Map requirements:
1) The map should be interactive, allowing the user to zoom and pan.
2) The map should display markers for relevant locations.
3) The map should update in real-time as new data (see data source requirements) becomes available.
4) The map should be responsive and work well on both desktop and mobile devices.
5) The map should have selectable layers for different map types (see data source requirements).
6) The map should be able to display the position of the user. This should be togglable from the map page.
7) There should be a scale bar.
8) Markers belonging to route files should be shown as small circles in the same colour as their route (not map pins). Team position markers (Garmin KML feed) should use a distinct marker shape - a diamond for now - each in its own palette colour.
9) Team markers whose "In Emergency" metadata is true should be shown at three times the normal size with a red outline.
10) The popup bubble for a team marker should have a "map" button at its bottom right that opens the reported location in the phone's mapping app.
11) Right-clicking (desktop) or long-pressing (touch) the map should open a small menu showing the coordinates of that point, with a "map" button that opens the location in the phone's mapping app (as for team marker popups).
12) Within the UK, the right-click/long-press popup and the Garmin team popup should also show an OS grid reference (2-letter sheet + 6 figures, e.g. TQ 302 796).
13) The start point set on the configuration page should be marked on the map with a small "home" icon (not a plain circle).

River levels requirements:
1) A "River levels" overlay should be available in the map menu overlays list (above Precipitation, which stays last), off by default unless enabled in configuration.
2) Data comes from the Environment Agency Flood Monitoring API (open data, no API key, England only): station list (with typical low/high range) and the latest level readings.
3) Each station is shown as a small arrow icon about the same size as the team diamonds (18px), coloured by level against the station's typical range: brown = below normal, green = normal, amber = above normal, red = at/above highest recent level, grey = no typical range available.
4) Selecting a dot opens a bubble with the station name, watercourse, level and unit, status text (e.g. "Within the usual range for this location"), time of the reading and a trend (rising / steady / falling, looked up when the bubble opens).
5) Data should load only when the overlay is first switched on, and readings refresh every 15 minutes while it is on. Station details are cached in the browser for 7 days.
6) Only stations inside a configurable box (north/south/west/east) are shown. The default box is a ~25 km radius around Dartmoor (50.345 to 50.795 N, 4.27 to 3.57 W); the box can cover the whole of England.
7) The configuration page should have a collapsible "River levels overlay" box with an on-by-default tick box, the four box edges as numbers, a map on which clicking two opposite corners draws a new box, and buttons to reset to the Dartmoor area or select the whole of England.
8) The arrow shows the level trend over roughly the last hour: rising = arrow pointing up, falling = arrow pointing down, steady (change under 1 cm) = arrow pointing right. Until the trend is known (or if unavailable) a small coloured dot is shown instead.
9) Trends are fetched per station for small areas (up to 150 stations) and from one bulk request for larger areas, so the arrows fill in shortly after the dots appear.

Garmin direct API requirements:
1) Team positions are retrieved primarily from Garmin IPC Outbound (push, no per-call cost). Garmin POSTs events DIRECTLY to the Worker route /ipc/outbound; no intermediate website or forwarding service (e.g. Anvil) is used. The Worker stores the latest position, battery, emergency state and last message per IMEI in KV and serves them to the map from /ipc/locations.
2) No secret ever reaches the browser. The map only reads /ipc/locations.
3) Both sources are used together, not as a primary/backup switch. The Garmin push feed and the MapShare KML feed (via the Worker relay) are both checked every poll. Positions are compared using their position timestamps; messages are compared using the message timestamp (`Message Time` in KML, not the KML position timestamp). If the KML message has no parseable message timestamp, prefer the timestamped push message when both sources contain one. If either source silently fails or falls behind, the other automatically takes over, and takes back over when it is current again. Position and message are chosen independently (the newest message may come from a different source than the newest position); the emergency state follows whichever source holds the team's newest event. KML events are matched to a team by IMEI where present, otherwise by display name. A team's popup states which source supplied its position.
3a) The KML feed is checked for updates every minute (garminPollIntervalMs = 60000). The push feed, which is a cheap read of the Worker's stored data, is checked every 10 seconds (garminPushPollIntervalMs = 10000) so that every position report is shown promptly (a route simulation sends one every 10 seconds); the last KML result is reused between KML checks. River levels, rainfall radar and other sources continue to be polled at their own intervals.
3b) Each team has two separate map markers. The position marker (diamond) is updated by every position report. The message marker (envelope, or a red pulsing "SOS" badge for SOS) is placed at the position where the team's latest message or SOS was received and is not moved by later position reports; it is replaced only when a newer message arrives, and removed when the message history is cleared. Its popup holds everything about that message: type (text, puck, SOS, SOS cancelled), content, time received, latitude/longitude, grid reference, elevation, speed, course, source (push feed or KML) and a link to open the location in a maps app. The KML source comparison uses its message timestamp rather than the timestamp of a later position update. The position popup does not carry the message. An open popup stays open when the map refreshes.
4) Marker names come from Device management (falling back to the IMEI). SOS (codes 4/6) marks a team as in emergency until cancelled (code 7); low battery and the last free-text message are shown in the popup.
5) The diagnostics panel states how many teams are currently shown from each source (push feed or MapShare KML), the operating mode, and any failure of either source. A status message appears on the map only if both sources fail.
6) Normal mode: /ipc/outbound accepts only requests carrying the static authorisation token (Worker secret IPC_OUTBOUND_TOKEN, compared with Garmin's X-Outbound-Auth-Token header or the Authorization header), with Content-Type application/json and a valid IPC Outbound body ("Events" array). Events for IMEIs not registered in Device management are ignored (still answered 200 so Garmin does not retry). If the token secret is not set the endpoint refuses traffic (503). /ipc/locations returns registered devices only. Incoming values are validated (IMEI format, coordinate ranges, body size, device count cap).
7) Test mode: unregistered IMEIs are also accepted and returned, shown using a grey dashed circle marked '?' (named 'Unregistered <IMEI>') instead of the team diamond; the token is always enforced. Unregistered devices never affect the KML/push comparison for registered teams. Test mode also enables the test tool that injects false team track information.
8) The mode ("normal" or "test", setting "mode", default normal) is chosen with a tick box in an "Operating mode" box on the configuration page, saved with "Save settings", and stored by the Worker (KV) when settings are saved; until then the Worker reads it from the committed settings.json.
9) Message-type handling: there should be an icon for each team in the same colour as the tracker that denotes the last message indication received, separately from the position tracking indicator
9a) When a free text message is received, the icon popout dialogue should display the message content and timestamp, allowing the user to quickly view the details without interfering with the map interaction.
9b) When message type 14 (puck message 1) is received, the icon popout dialogue should display the message "All ok" and timestamp, similar to free text messages, allowing the user to quickly view the details without interfering with the map interaction.
9c) When message type 15 (puck message 2) is received the icon popout dialogue should display the message "We're ok, but assistance needed" and timestamp, similar to free text messages, allowing the user to quickly view the details without interfering with the map interaction.
9d) When message type 16 (puck message 3) is received, the icon popout dialogue should display the message "Urgent Assistance required" and timestamp, similar to free text messages, allowing the user to quickly view the details without interfering with the map interaction.
10) SOS type messages should be further highlighted with a distinct icon or visual indicator to draw immediate attention and the popout dialogue should display the message content if any, "SOS" and timestamp, similar to other message types.

Note - Garmin Portal Connect (IPC Outbound) settings:
- Outbound URL: https://maynard-garmin-relay.maynardmaps.workers.dev/ipc/outbound (HTTPS, trusted certificate - provided by Cloudflare).
- Method / format: HTTP POST, JSON body (Content-Type: application/json), event schema V2 or later (V3/V4 are accepted).
- Authorisation: static authorisation token (not OAuth). The token value must equal the Worker secret IPC_OUTBOUND_TOKEN (set with: npx wrangler secret put IPC_OUTBOUND_TOKEN). Garmin Portal Connect sends it in the X-Outbound-Auth-Token header; the Worker also accepts the Authorization header. A "Bearer " prefix is accepted.
- Events to send: tracking/position reports, locate responses, free-text messages, puck messages 1-3 (codes 14-16), SOS (declare/confirm/cancel) and reference points for the devices listed in Device management.
- In Test mode, Garmin Portal Connect's Outbound SOS Test must be accepted even when Garmin uses an unregistered fake IMEI. Its test event (latitude 43, longitude -72) must be retained and exposed as a test SOS/message marker; Test mode must not require that fake IMEI to be registered.
- The Worker replies 200 for accepted traffic (including ignored unregistered IMEIs); 401 for a wrong token, 415/400 for malformed requests. Garmin retries failures after 2, 4, 8, 16, 32, 64 and 128 seconds, then pauses; after 5 days of failures delivery is suspended and Garmin support must resume it.
- The Garmin Portal Connect account must have only this URL configured as the Outbound destination.
- The Configuration page's Messaging section must include an "Unregistered trackers" entry that shows any received unregistered IMEIs and their latest position/message in Test mode, or clearly says that none have been received.
- The bottom of the unlocked Configuration page must have a "Location history" section showing the latest five received position reports or messages for every registered tracker and a separate unregistered-tracker entry. Each record must show event time, reported latitude/longitude when present, and the raw event body. Load the history when the section is opened and provide an explicit refresh control. This sensitive diagnostic data must only be available after passphrase verification.
- The test tool's Garmin delivery log must include the HTTP response and received request payload for each recent Outbound delivery, with headers recorded by name only (never token values). Retain a bounded recent log and cap payload size, clearly indicating truncation.

Note - messaging and tracking control (Garmin IPC Inbound):
- Messaging and tracking commands go through the Worker (POST /ipc/command, passphrase protected); the Garmin Inbound API key is never exposed to the browser.
- Use Garmin IPC Inbound V1 at https://eur-origin.explore.garmin.com:443/ipcinbound/V1 (Swagger docs: https://eur-origin.explore.garmin.com/IPCInbound/docs/), with HTTP Basic authentication. Store IPC_INBOUND_USER, IPC_INBOUND_PASSWORD, and IPC_SENDER as Worker secrets; IPC_SENDER is an email address. No credentials are sent to the browser.
- Send a text message with POST /V1/Messaging.svc/Message. The request has a Messages array; Recipients contains the 15-digit IMEI as a string, Sender is IPC_SENDER, Timestamp uses the .NET form /Date(<Unix milliseconds>)/, and Message is 1-160 characters. ReferencePoint is required and follows the known-working Portal Connect example: LocationType "0", Altitude/Speed/Course "1", Coordinate Latitude/Longitude 0, Label empty.
- Start/stop tracking with POST /V1/Tracking.svc/Tracking and Devices containing the IMEI as an integer, Tracking as a boolean, and Interval as an integer number of seconds (the page accepts minutes). Query status with GET /V1/Tracking.svc/Tracking?IMEI=<IMEI>. The status query and start/stop payloads have been checked against Garmin's current Swagger schema; the query has been verified live.
- The unlocked configuration Messaging section keeps a bounded Inbound command results log (last 30 commands), including endpoint and upstream HTTP status/response detail on failure. This is distinct from the test tool's Garmin delivery log, which records Garmin-to-Worker Outbound deliveries.
- Garmin delivers outbound messages and tracking changes over Iridium and bills them to the device plan, so in Test mode these commands are simulated by the Worker and never sent to Garmin. The Worker keeps the last 3 received messages per team and a command log (last 30).
- Only the Text message type can be sent to a device; puck and SOS messages are received only.
- A standard-library laptop diagnostic, tools/test_garmin_inbound.py, prompts for an IMEI and credentials (password hidden), then performs only a read-only GET tracking-status query against the EUR endpoint. It does not save credentials.
