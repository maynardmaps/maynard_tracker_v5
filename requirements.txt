1) Be as lightweight to open as possible so as to work with limited connectivity.
2) Be compatible with being hosted on github as a webpage.
3) Display a map to the user. See "map requirements" section for details.
4) Be responsive and work well on both desktop and mobile devices.



Map requirements:
1) The map should be interactive, allowing the user to zoom and pan.
2) The map should display markers for relevant locations.
3) The map should update in real-time as new data (see data source requirements) becomes available.
4) The map should be responsive and work well on both desktop and mobile devices.
5) The map should have selectable layers for different map types (see data source requirements).
6) The map should be able to display the position of the user. This should be togglable from the map page.
7) There should be a scale bar.
8) Markers belonging to route files should be shown as small circles in the same colour as their route (not map pins). Team position markers (Garmin KML feed) should use a distinct marker shape - a diamond for now - each in its own palette colour.
9) Team markers whose "In Emergency" metadata is true should be shown at three times the normal size with a red outline.
10) The start point set on the configuration page should be marked on the map with a small "home" icon (not a plain circle).

Data source requirements:
1) The map should be compatible with open street map, google maps and other common map providers.
2) The map should also be compatible with Ordnance Survey "Leisure Style" map layer. End point with API key (should be treated as secret): https://api.os.uk/maps/raster/v1/zxy/Leisure_27700/{z}/{x}/{y}.png?key=s2Jm0v3DoInYiNuQDnt6kw7K1VpfuxGE
3) The map should display KML markers from https://share.garmin.com/Feed/Share/9ZU7V - these should be updated in real time without having to refresh the webpage. These are known as "KML Markers"
4) The map should display a series of routes from either KML files or GPX files. These will be stored in sub-folders with names like "TT1", "TT2", etc within a "routes" folder.
5) The route sub-folder should be selectable, with a default set by the configuration page (see configuration page requirements).
6) All the routes in the selected sub-folder should be displayed on the map.
7) Routes should be displayed in different colours for clarity.
8) Routes should be able to be toggled on and off individually. Routes should default to toggled on.
9) The map should auto-center on the "start point" (see configuration page requirements).
10) The map should auto-zoom to fit all displayed routes and KML markers within the viewport.
11) "KML Markers" should be able to be toggled on and off individually. They should default to toggled on.
12) "KML Markers" should be selectable and, when selected, display the details of the marker from the source KML feed in a bubble.
13) "Weather data" is sourced from the UK Met office "weather data hub" api. The API key should be treated as secret and is <REDACTED - stored as Cloudflare Worker secret METOFFICE_API_KEY> 
14) The only type of weather data at this time is precipitation data sourced from the Map Images section of the weather data hub api. Precipitation data should be displayed on the map, sourced from the UK Met office "weather data hub" api. The order number on the API for this data is 	o102211703928
15) "Weather data" should be toggleable on and off individually. It should default to toggled off.
16) The map should be able to load a static KML file (known as "birds and rivers")with points and polygons from the folder "data" and display them on the map.
17) Birds and rivers KML file should be toggleable on and off individually. It should default to toggled off.
18) Where a single KML or GPX file contains more than one route (KML line placemarks, GPX tracks/routes), each route should be listed, coloured and toggled as a separate route in the menu rather than aggregated under the file's single entry.
19) Different "KML Markers" from the Garmin feed should be displayed in different colours.
20) Route and KML marker colours are configured as two generic palettes (one for routes, one for KML markers) of 8 colours each, not as colours for specific entries in the files currently loaded. The 1st entry (in alphanumerical order) takes colour 1, the 2nd takes colour 2, and so on up to 8.
21) Where a route file or KML marker feed has more than 8 entries, the palette colours should be repeated (the 9th entry takes colour 1, etc.).
22) The precipitation toggle should be the last entry in the overlays list on the map page.
23) When precipitation is shown, a timeline slider should let the user step through forecast times: one step per hour for the next 12 hours, then one step every 6 hours up to 48 hours.
24) Each timeline step should show the Met Office precipitation image valid closest to that time (preferring the most recent model run). Images should only be downloaded when selected, and cached for the session, to suit limited connectivity.
25) The timeline should have a play/pause button that continuously cycles through the precipitation timeline steps (looping back to the start). Moving the slider manually or hiding precipitation should pause playback.
26) The map should display an indication of the date/time (and offset from now) of the precipitation overlay currently shown, visible only while precipitation is displayed.
27) The "birds and rivers" overlay should load ALL the KML files in the "data" folder (not a single named file), and its single toggle should show/hide all of them. New KML files added to the folder should appear automatically without code changes.

Configuration page requirements:
1) The configuration page should allow the user to set the default route sub-folder.
2) The configuration page should allow the user to set the "start point" for the map. This should be configurable by entering coordinates or selecting a location on a map.
3) The configuration page should be accessible from the map page with a small button or link.
4) The configuration page should be responsive and work well on both desktop and mobile devices.
5) The configuration page should require a password to make changes to settings. This password should be "maynard".
6) The configuration page should allow the user to set colours for routes and KML markers by selecting colours from a colour picker.
7) The configuration page colour settings should be applied in the alphanumerical order in which routes and markers are listed.
8) The configuration page should provide a link to the github folder in which the project is stored.
9) The configuration page should provide toggles for which map sources are available for the map user to select.
10) Map sources should be displayed as a list on the configuration page, with the user able to add extra map sources to the list as needed.
11) The configuration page should have a clear "save settings" button that applies all changes made by the user.

Route management requirements:
1) The configuration page should have a "route management" section that lists all the route folders in the routes folder.
2) The folder list should be a fixed height and scrollable, so that an unlimited number of folders can be listed.
3) The user should be able to select a folder from the list.
4) For the selected folder, the page should list the files in that folder (in a fixed-height, scrollable list).
5) The user should be able to rename the selected folder.
6) The user should be able to delete the selected folder (including its files), after a confirmation prompt.
7) The user should be able to add a new folder.
8) The user should be able to add a new file (GPX or KML) to the selected folder.
9) The user should be able to select a file in the folder contents list, and rename or delete it (deletion after a confirmation prompt).
10) Route management changes should be committed to the GitHub repository by the Cloudflare Worker (the GitHub token must never reach the browser), should require the configuration passphrase, and should apply immediately without needing "Save settings".
